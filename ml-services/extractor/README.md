# Извлечение технологий и слабых сигналов

Сервис выделяет технологии в документах на русском и английском, склеивает упоминания,
находит дословные доказательства и оценивает стадию развития. Его вызывает `main-service`
в режиме `RADAR_CANDIDATE_SOURCE=ml`; как он встроен в поиск радара —
[ML_CLASSIFIER_HANDOFF.md](ML_CLASSIFIER_HANDOFF.md#источник-кандидатов-сервис-extractor). Публикации сервис не
ищет и карточки не пишет.

## Конвейер

```text
Документ: title, abstract, text, метаданные
    |
    +--> заголовок + аннотация --> XLM-R: BIO + роль + кандидат
    |                                  |
    |                           спаны с координатами
    |                                  |
    |                    имена, морфология, алиасы, F2LLM
    |                                  |
    +--> полный text ----------> доказательства по предложениям
                                       |
                             E5-large --> LR / temperature
                                       |
                                 стадия 0..5
                                       |
                счётчики корпуса --> тренд 1..3
                                       |
                      правила: балл, класс, уверенность, флаги
                                       |
                              /extract, /predict
```

Теггер читает заголовок и аннотацию окнами до 512 токенов с шагом 448; найденные спаны
привязываются к исходному `text` как `[start, end)` в символах, а не в байтах UTF-8. Край спана
внутри слова расширяется до целого слова, слово через дефис берётся целиком: иначе XLM-R
оставляет обрывки подслов вроде «adversar».

Канонизация склеивает русские словоформы, раскрытые в тексте сокращения и алиасы, близкие
названия — по эмбеддингам `f2llm-service` и сходству символов. Доказательства ищутся по
всему `text`, а не только по входу теггера; отсутствующий полный текст статьи это не
заменяет. Итоговая стадия — максимальная из подтверждённых цитатой; стадия 5 по фоновому
упоминанию требует прямого свидетельства массового применения.

## Модели

| Компонент | Вход → выход | Обучение и ограничения |
| --- | --- | --- |
| Теггер XLM-R | Токены заголовка и аннотации → BIO-метки, роли `background/contribution/application`, бинарная голова кандидата | 415 размеченных документов; F1 кандидатов 0,52 на тесте из 59 документов |
| E5-large-instruct + логистическая регрессия | Предложение с фиксированной инструкцией → эмбеддинг → вероятности стадий 0–5 после деления логитов на температуру | 1 541 размеченное предложение; стадии 3–4 представлены слабо |
| F2LLM-v2-0.6B | Названия → нормированные векторы размерности 1024 | Общий `f2llm-service`; модель и revision должны соответствовать бандлу |

F1 теггера — качество извлечения кандидатов, а не итогового ТОП-15. Коэффициенты LR,
инструкция и температура лежат в бандле; температура калибрует вероятности, но стадию не
меняет.

Стадии: **0** — нет подтверждения, **1** — идея/исследование, **2** — прототип,
**3** — пилот, **4** — ранняя коммерциализация, **5** — массовое применение.
Тренд: **1** — рост не подтверждён, **2** — рост, **3** — быстрый рост. Тренд считается
по отношению числа документов в двух соседних окнах: 12/12 месяцев или, если приходят
`growth_window: "6m/6m"`, `docs_recent` и `docs_previous`, — 6/6 месяцев. Пороги T1/T2 —
из бандла, для 6/6 они не калибровались. Любое повышение тренда требует не меньше трёх
документов в последнем окне (`MIN_TREND_RECENT_DOCUMENTS` в [rules.py](rules.py)): иначе два
документа против нуля давали бы тренд 2. `share_growth_pp` отношение не заменяет;
неизмеренное остаётся `null`.

## Правила оценки

[rules.py](rules.py) (`weak-signal-rules-v2`) считает:

- **Балл** `score = stage.code + trend.code`.
- **Класс**: шум — нетехнология или один маркетинг; недостаточно данных — нет
  подтверждённой стадии (в `/predict` это `noise` с причиной); стадия 5 — зрелая
  технология; иначе — слабый сигнал.
- **Уверенность** `value = P(стадия в диапазоне класса) × P(голова кандидата)
  × подтверждение документами × доля доверенных источников × (1 − штраф шума)`.
  - Для слабого сигнала берётся сумма вероятностей кодов 1–4, а не выбранного кода:
    колебание модели между соседними стадиями не должно ронять уверенность. Для стадии 5 —
    вероятность кода 5, ×0,6 при единственном фоновом источнике. Без распределения по кодам
    берётся вероятность выбранного кода, и объяснение это называет.
  - LR обучена с балансировкой классов, поэтому сумма p(1..4) завышена (в среднем 0,61 при
    фактической доле около трети), и температура этого не исправляет. Необязательный
    `p14_platt: {"a", "b"}` рядом с температурой (`stage_lr.json` у E5+LR,
    `stage_p14_platt` в `config.json` у HF-классификатора) применяет
    `p14 = sigmoid(a·logit(p14) + b)`, `a > 0`. Без него сумма идёт как есть.
  - Голова кандидата — средняя по токенам спана вероятность класса `candidate`, по
    кандидату — максимум по упоминаниям. Не измерена — множитель 1.
  - Подтверждение документами: 0 / 0,75 / 0,9 / 1 для 0 / 1 / 2 / ≥3 документов.
  - Неизвестное доверие — множитель 1 с отметкой в объяснении.
- **Флаги**: намерение, недостаток доказательств, маркетинг, нетехнология, единственный
  источник, стандарт (`has_standard`: ГОСТ, ISO, IEC, RFC и т. п.; стадию 5 сам не даёт).

Уверенность — не калиброванная вероятность и не балл. Порог `thresholds.predict` и версия
сервиса приходят из `release.json` бандла, в коде порога нет; как выбран порог — в разделе
«Проверка».

`RADAR_CLASSIFIER_VERSION` в Compose передаётся и в extractor: непустое значение, не
совпавшее с `service_version` бандла, не даёт сервису запуститься. Версия меняется только
вместе с бандлом и не должна совпадать с версией встроенной модели `main-service`
(`trend_live_classifier_weights.json`): сохранённый ответ одного классификатора иначе
прошёл бы за ответ другого.

## Фильтр имён

При запуске канонизатор читает [resources/name_stoplist.txt](resources/name_stoplist.txt) —
широкие области, нетехнологии и общие однословные существительные — и
[resources/name_allowlist.txt](resources/name_allowlist.txt) — известные сокращения.
Английский не лемматизируется, поэтому его формы перечислены явно (model/models); русские
имена сравниваются после лемматизации. Правила:

- со стоп-листом сверяются каноническое имя, поверхность упоминания и её алиас;
- белый список важнее стоп-листа, и сокращение проверяется само, а не через расшифровку:
  `PQC` не отсеивается из-за «post quantum cryptography» в стоп-листе;
- числа, стоп-слова и неизвестные латинские имена короче четырёх символов без второго
  токена кандидатами не становятся, если имени нет в белом списке и теггер не дал
  уверенность ≥ 0,8 для имени в заголовке.

Причины отсева остаются в `coverage.notes`.

## HTTP-контракты

Поля и валидация — [schemas.py](schemas.py); запросы и ответы глазами Go —
[фикстуры](../../backend/main-service/internal/application/testdata/ml_candidate_source).

`POST /extract` принимает документы и необязательный запрос:

```json
{
  "model_version": "weak-signal-2026-09-22.3",
  "query": "цифровые двойники",
  "documents": [{
    "doc_id": "d1", "source": "example", "lang": "ru",
    "title": "Цифровой двойник",
    "abstract": "Разработан прототип цифрового двойника."
  }]
}
```

Без `text` он собирается как `title + "\n\n" + abstract`. Ответ: `candidates`, `coverage`,
`model_versions`. Неочевидное в кандидате:

- `stage.probs` — вероятности кодов 0..5 для предложения, давшего стадию; `null`, если
  стадия не вычислена, равна 0 или распределение неизвестно. `stage.prob` для кода 5 может
  быть меньше `probs[5]`: множитель 0,6 применяется к `prob`, а распределение остаётся
  ответом модели.
- `head_prob` — число в [0, 1] или `null` (не измерено).

`POST /predict` оценивает уже выделенных кандидатов:

```json
{
  "feature_schema": "weak-signal-features-v1",
  "model_version": "weak-signal-2026-09-22.3",
  "candidates": [{
    "id": "c1", "name": "Цифровой двойник",
    "features": {"documents": 1, "scientific_works": 1,
      "market_records": 0, "active_periods": 1, "author_groups": 1,
      "top_group_share": 1.0, "share_growth_pp": null, "first_observed": null},
    "sources": [{"id": "d1", "title": "Цифровой двойник",
      "abstract": "Разработан прототип цифрового двойника."}]
  }]
}
```

Версии в примерах условные — подставьте `service_version` своего бандла. Ответ:
`feature_schema` и ровно одно `predictions[]` на каждый входной ID с `label`
(`weak_signal/mature/noise/failed`), `value`, `threshold`, `basis` и вкладами признаков.
Отказ модели даёт `failed` всему пакету, без частичных положительных оценок.

Необязательные поля `features` в `/predict` переносят решение `/extract`, посчитанное по
полному корпусу: счётчики окон роста (`docs_recent_12m`, `docs_previous_12m`,
`growth_ratio`, либо `growth_window: "6m/6m"` с `docs_recent`/`docs_previous`), стадия
(`stage_code`, `stage_quote`, `stage_prob`, `stage_probs`, `stage_model_version`),
`head_prob`, флаги (`only_marketing`, `not_a_technology`, `insufficient_evidence`,
`has_standard`, `single_source`; явное `false` отличается от отсутствия) и `source_trust`.
Без счётчиков тренд равен 1 («не измерено»); без стадии, флагов и доверия Python считает
их по переданным источникам. Стадия переиспользуется только при совпадении версии модели
стадии. `main-service` передаёт только базовые признаки из примера, а в режиме `ml`
`RADAR_CLASSIFIER_URL` оставляют пустым, и `/predict` не вызывается: вердикт даёт
встроенная модель.

Ошибки содержат русское `message`, частичный ответ не публикуется:

| Код | Когда |
| --- | --- |
| 409 | несогласованная версия |
| 400 / 422 | неверный пакет; 422 `cache_corrupted` — повреждённый кэш |
| 413 | `payload_too_large` / `response_too_large` |
| 503 | `storage_unavailable` — нет хранилища кэша спанов; отказ теггера на `/extract` |
| 504 | `timeout` — `/extract` не уложился в `EXTRACTOR_EXTRACT_TIMEOUT` |

Отказ модели стадии не роняет `/extract`: ответ помечается `degraded`, кандидат получает
`stage.status=failed`. У `/predict` свои слоты модели, поэтому оценка не ждёт за брошенным
извлечением. `GET /health` — версия, состояние хранилища и моделей; `GET /metrics` —
Prometheus. Веса грузятся в фоне: пока идёт загрузка, `/health` отвечает `degraded` с
HTTP 200, а Docker healthcheck ждёт `status=ok` (`start-period` 15 минут).

## Запуск

Нужны готовый бандл весов (в Git и образ не входит) и GPU: extractor занимает около 4 ГиБ
видеопамяти. Образ по умолчанию собирается на проверенном стеке torch 2.8.0+cu128 и
transformers 4.57.6 и запускается с `runtime: nvidia`; CPU-сборка — в комментариях
[infra/.env.example](../../infra/.env.example). В `infra/.env`:

```dotenv
EXTRACTOR_MODEL_BUNDLE_URL=https://example.org/extractor-bundle.tar.gz
EXTRACTOR_MODEL_BUNDLE_SHA256=<64 строчные шестнадцатеричные цифры>
EXTRACTOR_EMBEDDING_URL=http://f2llm-service:8085
```

Из корня репозитория:

```sh
docker compose -f infra/docker-compose.yml --profile ml-extractor up -d --build extractor
```

Compose даёт общий `postgres` для кэша спанов (миграция под блокировкой при старте),
`f2llm-service` и том `extractor-models`; наружу порт не публикуется. На стенде — точечное
обновление по навыку [deploy-stand](../../.claude/skills/deploy-stand/SKILL.md); после смены флагов радара пересоздайте
`main-service`.

| Переменная | По умолчанию | Смысл |
| --- | --- | --- |
| `EXTRACTOR_MODEL_BUNDLE_URL`, `EXTRACTOR_MODEL_BUNDLE_SHA256` | — | Обязательные URL архива (HTTP(S) или публичная ссылка Google Drive) и его SHA-256 |
| `EXTRACTOR_EMBEDDING_URL` | `http://f2llm-service:8085` | Базовый URL F2LLM, без `/v1/embeddings` |
| `EXTRACTOR_DEVICE` | `cuda` | Устройство теггера и E5 |
| `EXTRACTOR_CUDA_ATTENTION`, `EXTRACTOR_CUDA_DTYPE` | `sdpa`, `fp32` | Внимание и точность обеих моделей на CUDA; на CPU всегда eager/fp32 |
| `EXTRACTOR_TAGGER_CUDA_*`, `EXTRACTOR_STAGE_CUDA_*` | пусто | То же только для теггера или E5; важнее общих |
| `EXTRACTOR_TAGGER_BATCH_SIZE`, `EXTRACTOR_STAGE_BATCH_SIZE`, `EXTRACTOR_EMBEDDING_BATCH_SIZE` | 16, 8, 64 | Окон теггера, предложений E5 и имён в запросе к F2LLM за вызов |
| `EXTRACTOR_SLOTS` | 1 | Одновременных вызовов модели — отдельно на `/extract` и на `/predict` |
| `EXTRACTOR_PREDICT_TIMEOUT` | 27 | Секунды; меньше 30 |
| `EXTRACTOR_EXTRACT_TIMEOUT` | 290 | Секунды; меньше `RADAR_ML_EXTRACT_TIMEOUT` (300) у Go |
| `RADAR_ML_EXTRACT_MAX_REQUEST_BYTES`, `RADAR_ML_EXTRACT_MAX_RESPONSE_BYTES` | 4 МиБ, 1 МиБ | Пределы `/extract`, общие для Go и Python; у `/predict` те же, но фиксированные |
| `EXTRACTOR_POSTGRES_DSN` | из Compose | Вне Compose; без Postgres кэш спанов — в `EXTRACTOR_SPAN_CACHE_DIR` |

Батчи на GPU от 24 ГБ можно поднять в несколько раз, потолок — память под нагрузкой.
Паддинг задают корзины длины, поэтому размер батча меняет скорость, но не метки.

Режим CUDA вида `cuda:fp32:sdpa` входит в версии теггера и E5, а значит в ключи кэшей:
результаты разных режимов не смешиваются. SDPA и bf16 меняют последние знаки логитов
(ответы округлены до шести знаков). bf16 включайте только после проверки паритета на своём
GPU; первый кандидат — E5 (`EXTRACTOR_STAGE_CUDA_DTYPE=bf16`), для теггера паритет не
измерялся. Откат — `EXTRACTOR_CUDA_ATTENTION=eager`, `EXTRACTOR_CUDA_DTYPE=fp32`.

`EXTRACTOR_USE_STUBS=1` — детерминированная демонстрация без моделей и оценки качества;
`EXTRACTOR_COMPONENTS_FACTORY=module:function` подменяет сборку компонентов.

## Бандл весов

Бандл — tar с корневым `release.json`: версия сервиса, пороги, модели, SHA-256 каждого
файла. Внутри XLM-R с головами, E5, `stage_lr.json` и `e5_lr_coefficients.npz`. При запуске
`container_entrypoint` проверяет SHA архива, пути и суммы файлов и атомарно ставит бандл
в том; при несовпадении сервис не стартует. Реестр моделей строится из `release.json`
в `/var/lib/extractor/models/registries/<SHA256>.yaml`.

Обновление: новые URL и SHA-256, `RADAR_CLASSIFIER_VERSION` = `service_version` нового
бандла, пересоздать `extractor` и `main-service`. Любая смена весов, порогов или вычислений
требует новой версии сервиса. Старый бандл остаётся в томе для отката. Для смонтированных
заранее весов — `EXTRACTOR_MODEL_SOURCE=local` с явным `EXTRACTOR_MODELS_YAML`
([models.yaml](models.yaml) — реестр для такого запуска и тестов); URL и SHA тогда пустые.

## Кэш и пределы ответа

Кэш спанов — Postgres (или каталог), ключ `text_sha256 + model_version`; конфликт
содержимого не перезаписывается. Кэш доказательств и стадий — в памяти процесса (до
100 000 записей, около 128 МиБ). Версии раскодирования спанов и вердикта стадии входят
в ключи, поэтому записи прежнего формата тёплым ответом не выдаются, а некорректные и
частичные результаты кэш не прогревают.

Ответ несёт до 24 доказательств на кандидата, до 2 000 знаков на цитату и 24 000 суммарно;
цитата итоговой стадии в приоритете, признаки считаются по всем доказательствам до
сокращения.

## Проверка

Тесты проверяют контракты на фикстурах и малых синтетических моделях — не качество
обученных весов, не GPU и не живой Postgres. Из корня репозитория:

```sh
pip install -r ml-services/extractor/requirements-dev.txt
PYTHONPATH=ml-services python -m pytest ml-services/extractor -q -p no:cacheprovider
```

Порог 0,35 выбран так: записанные на стенде запросы `/extract` и `/predict` пересчитаны на
весах бандла (формула `weak-signal-rules-v2`, модель стадии stage-v3, калибровка Platt);
15 опубликованных кандидатов размечены вручную: 8 верных, 3 частично верных, 4 неверных.
«Строго» — точность и полнота по верным, «мягко» — по верным и частично верным; полнота
считается среди этих 15, а не среди всех технологий корпуса.

| Порог | Прошло из 15 | Строго: точность / полнота | Мягко: точность / полнота |
| ---: | ---: | --- | --- |
| 0,30 | 11 | 0,55 / 0,75 | 0,82 / 0,82 |
| **0,35** | 10 | **0,60 / 0,75** | 0,80 / 0,73 |
| 0,40 | 9 | 0,56 / 0,63 | 0,78 / 0,64 |
| 0,45 | 6 | 0,50 / 0,38 | 0,83 / 0,45 |
| 0,50 | 4 | 0,50 / 0,25 | 1,00 / 0,36 |

На 0,35 лучший строгий F1 (0,67); порог 0,40 и выше теряет верные технологии, не повышая
точность. Оставшиеся ошибки (уверенность 0,42–0,48) — дубль полного имени и общая фраза:
их отделяют канонизация и стоп-лист, а не порог. Выборка мала и отобрана прежним порогом,
поэтому порог предварительный — перепроверить на новой разметке.
