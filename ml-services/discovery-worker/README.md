# discovery-worker

Создаёт дополнительные гипотезы без ручного запуска, когда корпус изменился и загрузка
затихла. Нужна модель генерации: без `VLLM_URL` воркер простаивает — шаблонных гипотез
нет.

## Режимы

`DISCOVERY_MODE=transfer` (по умолчанию) переносит сильную гипотезу с одного KPI на близкий
KPI, которому не хватает покрытия: сравнивает цели по эмбеддингам, берёт сильные гипотезы
близкой цели, адаптирует их моделью. `graph-compute` не нужен.

`DISCOVERY_MODE=bridge` вызывает `ScoreBridges` в `graph-compute`, получает пары тем с
документами-посредниками и просит модель сформулировать проверяемую гипотезу. Параметры
графа совпадают с `cluster-worker`, чтобы мосты ложились на темы доски.

Гипотеза публикуется только если у неё есть реальные источники, она не пересказывает
существующий текст корпуса (сходство не выше `NOVELTY_MAX_SIM`), а в режиме `bridge` у неё
несколько документов-посредников. Новизну проверяют эмбеддинги, а не самооценка модели.

## Настройки

Значения по умолчанию — в `infra/docker-compose.yml`. Неочевидное:

| Переменная | Смысл |
| --- | --- |
| `AUTO_DISCOVERY` | главный выключатель |
| `DISCOVERY_LIMIT` | гипотез за запуск |
| `NOVELTY_MAX_SIM` | максимум сходства с существующим текстом |
| `TRANSFER_MIN_SIM`, `TRANSFER_COVERAGE_FULL` | насколько близки цели и когда цель считается покрытой |
| `TRANSFER_PER_PAIR`, `TRANSFER_MAX_PAIRS`, `TRANSFER_MIN_GAP` | переносов на пару, пар за запуск и на сколько гипотез у донора должно быть больше |
| `BRIDGE_*` | отбор мостов в режиме `bridge` |

## Проверка

Доска `/hypotheses` в интерфейсе, логи и проверка без внешних запросов (из
`ml-services/discovery-worker`):

```bash
docker compose -f ../../infra/docker-compose.yml logs --tail=120 discovery-worker
PYTHONPATH=../runtime python worker.py --selfcheck
```
