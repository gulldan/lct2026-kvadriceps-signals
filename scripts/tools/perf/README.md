# Нагрузочный замер каталога технологий

`technology-catalogue-load.sql` наполняет базу синтетическим корпусом целевого объёма: 2 000
документов, 100 000 технологий, 50 000 синонимов, 1 000 000 упоминаний. Тексты сгенерированы, но
длины и словарь близки к реальным: латентность зависит от размера строк и селективности `LIKE`, а
не от смысла. Объём задают переменные psql `docs`, `techs`, `mentions`.

Гонять **только на одноразовой базе**. Скрипт вставляет и удаляет строки по префиксу `ops07-`,
но миллион строк в демонстрационной базе оставит раздутые таблицы и синтетические технологии в
каталоге у любого зрителя. `measure.sh` пересоздаёт базу `ops07` целиком (`DROP DATABASE`),
поэтому имя базы менять только осознанно.

## Прогон

Миграции применяются к дампу схемы стенда, а не к живой базе:

```sh
docker exec rag-platform-postgres-1 pg_dump -U rag -d rag --schema-only \
  --no-owner --no-privileges > /tmp/schema.sql
```

Дальше всё делает `measure.sh` (контейнер `rag-ci-pg`, база `ops07`; меняются через `PGC`, `DB`,
`SCHEMA`, `CLIENTS`, `SECONDS_PER_RUN`):

```sh
./measure.sh sweep                      # таблица объёмов, затем порог на целевом
./measure.sh prepare 100000 1000000     # только наполнить целевым объёмом
./measure.sh single                     # один пользователь, пять форм запроса
./measure.sh prepared                   # подготовленный оператор: custom- и generic-план
./measure.sh p95                        # 10 параллельных, p50/p95/p99 по pgbench
./measure.sh explain 'сепарация'        # EXPLAIN ANALYZE одной формы
```

Порог — p95 поиска не больше 2 с при десяти параллельных пользователях.

`prepare` создаёт индексы каталога **после** загрузки, из файлов миграций `00037` и `00038`, а
не из копии: миллион строк в готовый GIN грузится втрое дольше.

`prepared` гоняет запрос так, как сервис: pgx держит именованные подготовленные операторы, и
после пятого исполнения Postgres может перейти на generic-план, который не знает значений
параметров. Если generic-план хуже custom-плана, это видно здесь, а не в продакшене.

Формы запроса: общий термин, узкий термин, попадание только в синоним, весь каталог
(`all=true`) и худший случай — термин, который есть в описании каждой технологии. Последний
меряется не ради порога, а чтобы знать потолок.

## Откуда берётся запрос

`catalogue-sql.py` читает `catalogueSearchSQL` и `catalogueAllSQL` прямо из
`backend/db-service/internal/infrastructure/postgres/technology_catalogue.go` и подставляет
литералы вместо параметров. Копия запроса разошлась бы с кодом, и замер перестал бы что-либо
значить. Пустой `--term` даёт запрос «весь каталог» — в коде это отдельный оператор.
