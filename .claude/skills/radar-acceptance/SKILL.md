# Приёмка живого поиска

Обычная приёмка богатой темы требует **ровно 15 технологий**. Семь результатов
не проходят TOP-15, даже если все семь карточек корректны. Выдача `search-v25` добирает
до пятнадцати кандидатами ниже планки с пометкой `shortfall {code, reason}`; строгий режим
их принимает, но считает отдельно — доля проверенных видна в строке «Проверенных». Скрипт
проверяет контракт `search-v25`; предметную корректность технологий и цитат оценивают отдельно.

Перед запуском задайте `STAND_URL`, `STAND_USER` и `STAND_PASSWORD` в приватном
окружении. Вместо пары пользователя и пароля можно использовать `STAND_TOKEN`.
Скрипт также читает приватный файл, указанный в `STAND_ENV_FILE`; переменные процесса
имеют приоритет. Значения не хранить в навыке, аргументах команды или отчётах.

```sh
STAND_ENV_FILE=infra/.env python3 scripts/radar-acceptance.py \
  --fresh --out result.json "твердотельные аккумуляторы"
```

Пароль выдаёт организатор показа. Для существующей переменной с токеном поддерживается
`--token-env ACCESS_TOKEN`: передаётся только имя переменной. Флаги `--password` и
`--token` со значениями отклоняются. `--base` и `--user` оставлены для совместимости
и принимают только значения, уже заданные в окружении.

Скрипт логинится, запускает поиск и опрашивает его каждые 5 секунд. Сохранённый ответ
обезличивается по настройкам окружения; его предметные цитаты всё равно нужно
проверить перед публикацией.

Общий срок ожидания — 900 секунд (`--timeout`), включая фоновые переводы и дооценку.
Ответ `ready` с `digests_pending` или `rescoring` ещё опрашивается без нового
`refresh` до снятия обоих признаков. Затем применяется полный контракт: отсутствие
перевода после завершения фоновой работы остаётся провалом. Время ожидания и
свидетельства свежего сбора сохраняются за весь запуск, без сброса при первом `ready`.

После деплоя используйте `--fresh`: флаг отправляет `refresh=1` до первого принятого
запуска, повторяя его только пока сервер занят; после допуска опрос идёт без
`refresh`. HTTP 429 не считается допуском. Уже работающий поиск не перезапускается.
Для доказательства нового сбора нужны запрос обновления, наблюдение `running`
с начальным `elapsed_seconds` от 0 до 5 без `reopening` и дата `detail.observed_at`
не раньше запуска проверки и не позже её завершения. Эти сведения сохраняются
в `timing`: `refresh_requested`, `saw_running`, `first_running_elapsed_seconds`,
`started_at`, `completed_at`, `observed_at`, `fresh_collection_proven`.

При `--fresh` отсутствие такого доказательства проваливает приёмку: мгновенный
ответ из кэша не считается новым сбором. Без флага живой поиск всегда сохраняет
`fresh_collection_proven=false`, даже если пришлось дождаться результата.
`--fresh` несовместим с `--detail-file`; чтение готового файла не запускает сбор.

## Режимы и повторная проверка

Сохранённый ответ можно проверить без нового живого поиска:

```sh
python3 scripts/radar-acceptance.py --detail-file result.json
```

По умолчанию действует строгий режим `top15`: меньше или больше 15 — провал.
`--require-model` дополнительно требует модельную оценку каждой принятой карточки,
её происхождение, признаки и согласованные счётчики. Без этого флага отсутствие
модели отмечается предупреждением, а доля правил не выдаётся за модельную оценку.
Промежуточный `classifier_unavailable` остаётся видимым предупреждением, если
после добора каждая принятая технология имеет полную оценку текущей версии.
Отсутствующая, некорректная или устаревшая итоговая оценка по-прежнему проваливает
`--require-model`; история отказавшей волны не заменяет проверку итоговых карточек.
Метка `insufficient_data` и непустой `data_gap` означают воздержание модели,
а не решение по данным: при `--require-model` любая такая карточка проваливает
проверку. Без этого флага ответ остаётся доступным для диагностики с явным
предупреждением. Полнота трёх полей карточки и подтверждающих цитат проверяется
отдельно и не заменяет модельного решения.

Консоль различает число ответов классификатора (`model_scored` из API,
включая воздержания) и число решений по данным без воздержания
(`validation.model_decisions`). Наличие двенадцати ответов «мало данных»
означает ноль модельных решений. Счётчики исходного API не изменяются.

Явные контрольные режимы:

```sh
# Проверить структуру неполного результата; это не приёмка TOP-15.
python3 scripts/radar-acceptance.py --detail-file result.json --allow-shortfall

# Проверить заранее выбранный пустой контроль с объяснением отсутствия результатов.
python3 scripts/radar-acceptance.py --detail-file empty-control.json --expect-empty
```

`--allow-shortfall` допускает от 1 до 15 результатов только для диагностики;
пустая выдача и 16 результатов проваливаются. `--expect-empty` требует ноль
результатов и объяснение в ограничениях или списке исключённых. Флаги
взаимоисключающие; совместное использование отклоняется до поиска.

В сохранённом JSON `validation.acceptance_mode` различает `top15`,
`shortfall_diagnostic` и `empty_control`. `validation.passed` относится к выбранной
проверке, а `validation.top15_passed` бывает `true` только после успешной обычной
приёмки. В обоих контрольных режимах оно всегда `false`, даже при 15 карточках;
консоль явно сообщает «TOP-15: НЕ ПРИНИМАЛСЯ». Диагностический успех не заменяет
повторную обычную приёмку.

Код возврата `0` означает успех выбранной проверки, `1` — невыполнение контракта
или ожидания, `2` — неверные аргументы либо невозможность прочитать ответ.

## Что считается провалом

Код возврата `1`, если нарушено хотя бы одно ожидание задания:

- в обычном режиме количество технологий не равно 15;
- отсутствует ID принятой технологии, повторяются ID или названия технологий
  (регистр, `ё`/`е`, пробелы и пунктуация не различают название; буквы и цифры версий сохраняются);
- счётчики не соответствуют карточкам и источникам;
- отсутствуют обязательные квалификация, происхождение, источники или проверенные цитаты;
- отсутствует общий план запроса, квалификация v6 использует другой `scope` либо прямые
  источники не подтверждают требуемые ветви и все общие условия; неизвестные и повторные
  ID критериев также проваливают проверку;
- отсутствует любое из трёх обязательных русских полей: описание, преимущество
  или кейс; каждое должно иметь проверенную цитату, `missing` не заменяет поле;
- карточка помечена неполной непустым `missing`;
- нарушены действующие проверки рынка, правил или модельной оценки.

Диагностический флаг меняет ожидание количества, но не разрешает дубли,
сломанные ссылки на источники, несогласованные счётчики или некорректные оценки.

Технология без `shortfall` проходит полную проверку квалификации, релевантности,
согласованности и цитат. Добранная с `shortfall` полной квалификации не требует,
но в любом режиме проваливает приёмку, если:

- код причины вне белого списка `below_top`, `classifier_rejected`, `classifier_unavailable`,
  `incomplete_card`, `thin_evidence`, `one_group`, `unassessed`, `qualification_budget`,
  `qualification_unavailable`; коды `mature`, `market_formed`, `long_history`, `well_known`,
  `not_technology`, `off_topic`, `duplicate`, `incoherent_evidence`, `hype` в добор не
  попадают — это зрелое, повторное, чужое по теме или шум;
- нет русской причины, русского описания или хотя бы одного источника;
- модель назвала её зрелой (`mature`) или рынок сформирован.

У каждой из пятнадцати источники обязаны иметь название, дату, URL и паспорт из шести полей:
`language`, `language_basis`, `publisher_type`, `genre`, `trust`, `trust_basis`
(иностранный — ещё русский пересказ и имя модели). Счётчик `top_up` равен числу добранных,
`above_threshold` считает только проверенные.

Вердикт «слабый сигнал» и счётчик `model_above_threshold` требуют двух независимых
подтверждений: разных авторских групп или разных издателей рыночных записей — все статьи
одной группы считаются одним источником (как `liveIndependentSources` на сервере).

ТЗ допускает один или несколько источников. Одного прямого подтверждающего источника
достаточно; контекстная статья, обзор или другой механизм его не заменяют. Полный
паспорт источника, основание доверия и русский пересказ иностранного материала
по-прежнему обязательны. Ограниченное доверие к единственному слабому источнику
должно быть видно в паспорте; число источников само по себе не доказывает качество.

`mode=any` требует хотя бы одну подтверждённую ветвь, `mode=all` — все ветви;
общие `required` обязательны в обоих случаях. Смысл самого плана нужно сверить с запросом:
корректный JSON не доказывает, что модель сохранила отрасль или не добавила лишнее условие.
При наличии `canonical_name` проверяется буквальность имени в выбранном первоисточнике.
Если исходная аннотация не возвращена, выдаётся предупреждение о непроверенном имени,
а отсутствие оригинала не объявляется подтверждением.

Для карточек с `source_contexts` приёмка проверяет точный сохранённый текст и его SHA256,
принадлежность источнику карточки, ID и версию arXiv, URL, вид покрытия и диапазоны.
Цитаты карточки сверяются с этим текстом. Квалификация технологии по-прежнему должна
иметь собственные исходные свидетельства: поздний полный текст не подменяет её проверку.
`abstract` с причиной недоступности HTML остаётся допустимым контекстом, но не означает
полнотекстовую проверку. `fulltext` и `excerpted_fulltext` показывают объём прочитанного,
а не истинность утверждений. Скрипт не восстанавливает исходный HTML из одного хеша;
для предметной приёмки нужно отдельно открыть первоисточник и проверить смысл,
условия, метрики и ограничения всех пятнадцати карточек.

Для открытых работ Zenodo ответ `search-v25` сохраняет `source_revisions`: запрошенный,
точный и общий DOI, адрес записи и API, даты обновления и получения, целое авторское
описание и хеши. Общий DOI разрешается в текущую версию, закреплённый DOI остаётся
своей версией. Скрипт проверяет связь с работой, адрес, даты, текстовый хеш и цитаты
по возвращённому описанию. `publisher_metadata` не означает чтение PDF или независимую
проверку авторских результатов. Ошибка обновления или исчерпанный бюджет исключает
такой источник из отбора с явной оговоркой; старая аннотация не подставляется.

## Что смотреть глазами в выводе

| Строка                 | На что смотреть                                                                       |
| ---------------------- | ------------------------------------------------------------------------------------- |
| Отобрано               | ровно 15; недобор проваливает обычную приёмку, причины нужно исследовать отдельно     |
| Проверенных            | доля прошедших все проверки; добранные ниже планки — кандидаты для эксперта, их коды  |
| Кандидаты              | сколько из статей, из направлений карты (`direction:`) и из рыночных записей (`rec:`) |
| Источников обработано  | сколько записей ответа прочитано; выше 75 % правил — только среди проверенных         |
| Ответов классификатора | ответы модели, решения по данным без воздержаний и вердикты «слабый сигнал»           |
| ОШИБКА / ПРОВЕРИТЬ     | нарушение контракта проваливает приёмку; предупреждение требует ручной сверки         |

## Грабли

- Живой поиск выполняется по одному: «радар занят» означает чужой запрос, а не отказ — подождать
  и повторить, а не запускать второй.
- Не перезапускать сборщик источников во время сбора: недобранный снимок затрёт удачный.
- Отказ канала — это названное ограничение в «Границах сбора», а не ноль; пустой канал без ключа
  не считается провалом приёмки.
