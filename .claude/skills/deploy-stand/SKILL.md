# Деплой на стенд

Стенд — наш: разрешения спрашивать не нужно, но и полный перезапуск контура делать нельзя.

## Перед выкладкой

Прогнать проверки (навык `verify-before-commit`) и влить правку в `develop`. На стенд
выкладывается то, что уже в ветке, а не рабочее дерево.

## На сервере

Деплой идёт целью `make deploy`: она сама собирает набор `-f` (базовый compose, оверлей
корпоративного CA, если в `infra/.env` заполнен `RAG_CA_BUNDLE`, и локальный оверлей стенда) и
сама ставит `BUILDX_BUILDER=default` — на стенде настроен builder `multiarch`, который не
поднимается, и сборка падает ещё до первого слоя. Руками набирать `docker compose -f
infra/docker-compose.yml …` нельзя: без второго `-f` корпоративный сертификат бесшумно
снимается с 19 сервисов.

Деплоить нужно из того чекаута, из которого сервис поднят. Пути задаются только в
приватном окружении: `STAND_RADAR_DIR` для радара, `STAND_APP_DIR` для остальных сервисов,
`STAND_DATA_DIR` для хранилищ и мониторинга. Перед выкладкой сверить их с меткой контейнера
(`docker inspect <контейнер> --format '{{index .Config.Labels "com.docker.compose.project.config_files"}}'`),
иначе compose пересоздаст сервис по чужому дереву; вывод содержит внутренние пути и не должен
попадать в публичный отчёт.

```sh
set -a
. "${STAND_ENV_FILE:?укажите приватный файл окружения}"
set +a
cd "${STAND_RADAR_DIR:?задайте путь чекаута радара}"
git status --short
git fetch origin develop
git merge --ff-only origin/develop
make deploy SERVICES="main-service radar-analysis radar-collector frontend"
make ps
```

`main-service`, `radar-analysis` и `radar-collector` деплоятся ТОЛЬКО вместе: они собираются из
одного дерева и строги к полям запроса друг друга. 17.09 сборщик, оставшийся на старом образе,
сутки падал с `unable to unmarshal JSON object into Go string within "/limits/0"`, снимок радара
не обновлялся, а все контейнеры при этом были «здоровы».

Чужие незакоммиченные файлы в чекауте — не сносить: убрать в `git stash`, обновиться, вернуть.

## Полное обновление

Идёт через серверную обёртку `compose`: она хранит `--env-file` чекаута, набор `-f` (базовый
compose, `docker-compose.corp-ca.yml`, серверный GPU-оверлей) и профили. Сначала — копия из
раздела ниже.

```sh
git status --short                               # локальных правок быть не должно
git fetch origin develop && git merge --ff-only origin/develop
compose config --quiet && compose build          # нужен запас диска от 60 ГБ
compose up -d --no-build && compose ps
```

Точечно через обёртку — `compose up -d --build <сервисы>`.

## Бэкап и откат

Перед полным обновлением сохранить в каталог, доступный только владельцу, и держать до приёмки:
тома `pgdata`, `rabbitmqdata`, `valkeydata`, `seaweedfsdata`, `qdrantdata`, `osdata`, `promdata`,
`grafanadata`; `infra/.env`; `git rev-parse HEAD` и `git diff` чекаута; список образов, а текущие
образы пометить тегом с хешем коммита.

Откат: остановить только этот compose-проект, вернуть коммит и `.env`, поднять старые образы по
тегам. Миграции `db-service` (goose, при старте) назад не откатываются — версия приложения должна
совпадать со схемой БД. Тома восстанавливать только на остановленном контуре и после отдельной
копии текущего состояния: восстановление отменит всё, что записано после копии.

## Что нельзя

- **`make up` на живом стенде.** Он повторяет `env-bootstrap`, и пароль Postgres в `infra/.env`
  разойдётся с паролем в томе `pgdata` — контур ляжет.
- `make clean`, `down -v` и глобальная очистка Docker: удаляют тома вместе с данными, для отката
  не нужны.
- Класть `infra/.env` из Git или из соседнего чекаута: файл живёт только на сервере, выкладка —
  явным списком файлов, не синхронизацией каталога.

## Проверка после

```sh
compose ps
curl --silent --show-error --fail "${STAND_HEALTH_URL:?задайте адрес проверки API}"
curl --silent --show-error --fail "${STAND_URL:?задайте адрес фронтенда}/healthz"
docker inspect rag-platform-<сервис>-1 --format '{{range .Mounts}}{{.Destination}} {{end}}'
make demo-smoke   # готовность без трат на генерацию; RAG_API_BASE=http://127.0.0.1:8081/api/v1
```

У каждого сервиса из оверлея корпоративного CA в монтированиях должен быть
`/etc/rag/trust-bundle.pem`: без него LLM-шлюз падает с `x509: unknown authority`, ничего при этом
не роняя. На стенде `HTTP_PORT=8081` (8080 занят другим проектом); наружу открыт только `:5173`.

После изменения окружения пересоздать затронутые сервисы; `S3_PUBLIC_ENDPOINT` читают и API, и
nginx фронтенда, поэтому при его смене — оба. Адреса, ключи и контакты читаются только из env. В
админке проверить модель и обычные параметры: только разрешённые несекретные настройки могут
переопределять окружение.

Приёмка живого поиска после деплоя радара — навык `radar-acceptance`; глазами — войти, задать
запрос на `/trends`, открыть технологию и выгрузку.
